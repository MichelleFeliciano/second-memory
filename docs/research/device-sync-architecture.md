# Research Brief: Phone/Computer Sync Architecture

## Question

The app currently runs as static files with `localStorage` as the only persistence
(fully offline, zero network calls). The user wants to access the app from their phone
and have phone and computer share the same data, with the requirement that the phone
keeps working fully offline when the computer (the would-be sync server) is off, and
automatically resyncs when the computer comes back online. This deliberately relaxes
the "no calls to any remote server" constraint for a **self-hosted** sync server, while
everything else (zero npm/CDN dependency, no build step, tight scope) should hold as
much as possible. Five sub-questions were asked; each is answered below.

Context gathered from the repo: all nine collections already go through shared
`loadCollection(key)` / `saveCollection(key, items)` helpers (`app.js` lines 11–23)
against `localStorage`, storing a flat JSON array per collection. Every record already
carries a stable `id` generated by `makeId()` (`crypto.randomUUID()` with a fallback),
confirmed at 10 call sites across all nine collections. That stable per-record id is
load-bearing for everything below — sync only works because records already have
identity independent of array position.

## 1. Conflict resolution for 2-device (later N-device) offline-first sync

**The premise to get right first:** because sync goes through a single self-hosted
server (phone → server ← computer), this is a **hub-and-spoke** topology, not
peer-to-peer/multi-master. That matters a lot: hub-and-spoke lets the server act as the
single arbiter of "what version is current," which is a much simpler problem than true
multi-master replication (which is what CRDTs and vector clocks exist to solve).

**Finding — LWW-Register, what it is:** Last-write-wins is a standard, well-documented
conflict-resolution pattern: each write carries a timestamp, and on conflict the write
with the later timestamp is kept, the other discarded. **Confirmed** as a standard,
named pattern (used by systems like Cassandra/DynamoDB-style stores); see the general
description and its known "lost update problem" — a write's effect can be silently
never observed because a later concurrent write clobbers it — in the review at
[oneuptime.com — How to Implement Last-Write-Wins](https://oneuptime.com/blog/post/2026-01-30-last-write-wins/view)
and the GitHub issue thread describing the exact same failure mode in a real app,
[cruciferousgreens/workout-app#293 — "LWW conflict resolution uses device wall-clock (clock skew bias)"](https://github.com/cruciferousgreens/workout-app/issues/293).

**Finding — what LWW gets wrong, precisely:**
- **Clock skew is a real ordering bug, not a theoretical one.** If device A's clock is
  slow, a write it makes *after* device B's write can be assigned an *earlier*
  timestamp, so a naive `if (incoming.updatedAt > stored.updatedAt)` comparison keeps
  the objectively-older edit and silently discards the newer one. **Confirmed** — this
  is the exact mechanism described in the sources above.
- **Silent data loss on genuine concurrent edits.** If both devices edit the *same
  record* while both are offline (e.g., edit a medication's dosage on the phone, then
  edit the same medication's dosage on the laptop before either has synced), LWW
  discards one edit entirely with no notice to the user. **Confirmed** as the "lost
  update problem" per the sources above.
- **What it gets right:** no merge UI, no per-field diffing, trivial to implement and
  reason about, and for the *overwhelming majority* of this app's real usage (editing a
  to-do on the phone on the bus, editing a book rating at the computer later — never the
  same record on both devices in the same offline window) it produces the correct
  result with zero extra work. **Confirmed** as the acknowledged trade-off in all LWW
  literature reviewed.

**Finding — logical/monotonic counters as a clock-skew mitigation:** A Lamport
timestamp / logical clock is a well-established, much older (1978) technique for
ordering events across machines *without* relying on synchronized wall clocks: each
process keeps an integer counter, increments it before each local event, and on
receiving a message from another process takes `max(local, incoming) + 1`. **Confirmed**
— see [Lamport timestamp — Wikipedia](https://en.wikipedia.org/wiki/Lamport_timestamp),
summarizing Lamport's original 1978 paper. Its documented limitation: it gives a total
order but cannot by itself tell you whether two events were truly *concurrent* (that
needs a vector clock, one counter per device) — **Confirmed**, same source. Vector
clocks / version vectors solve the "was this actually concurrent" question precisely,
and are the standard technique Dynamo-style multi-master stores use for this — see the
worked "version vector" explanation in the search summary from
[sookocheff.com — Vector Clocks](https://sookocheff.com/post/time/vector-clocks/) and
[designgurus.io — vector clocks vs Lamport timestamps](https://www.designgurus.io/answers/detail/when-to-use-vector-clocks-vs-lamport-timestamps).
That said, full vector clocks are designed for *multi-master* topologies where any
replica can accept a write independently — this app's hub-and-spoke shape means a
lighter mechanism suffices (see recommendation).

**Recommendation (concrete, not over-engineered):**
Do **not** use wall-clock timestamps as the source of truth for ordering, and do **not**
build a CRDT or a full vector clock. Instead, use **server-assigned optimistic
concurrency control** — the same idea behind HTTP's `ETag`/`If-Match` conditional
requests (RFC 7232), just carried in the JSON body instead of HTTP headers, since the
sync endpoint is a single batch call rather than per-resource REST calls:
- Every record gets a `version` integer, starting at 1, **owned and incremented only by
  the server** (not by either device's clock) every time it accepts a write to that
  record. This sidesteps clock skew entirely — the server's own counter is the single
  source of truth, and no two devices' clocks ever need to agree.
- Each device remembers, per record, the `version` it last synced (`baseVersion`).
  When it pushes an edit, it sends `baseVersion` along with the new data.
- On receiving a write, the server checks: does `baseVersion` match the record's
  current stored `version`? If yes, accept, bump the version, done — this is the common
  case and costs nothing extra. If no (someone else's write landed on this record
  since this device last synced), a genuine concurrent edit has been detected.
- **On a genuine conflict** (rare, by this app's own usage profile — personal,
  single-user, not real-time collaborative): do not silently discard either write and
  do not build a merge UI. Instead, **keep both**: apply the version the server already
  has as canonical, and save the incoming conflicting write as a separate, clearly
  flagged duplicate record (e.g. append `" (synced copy — please check)"` to a
  title/name field, or a small `_conflict: true` marker the UI can surface) so the user
  loses nothing and can manually reconcile it later, at their convenience. This pattern
  — surface conflicts as visible duplicates rather than a silent overwrite or a forced
  merge dialog — mirrors the well-known approach several real sync tools take (Dropbox
  "conflicted copy" files are the most visible public example). This is **Unverified**
  as a claim about Dropbox's exact internal implementation (not independently verified
  against Dropbox's own documentation in this pass) but is included as prior art for the
  *shape* of the mitigation, not as a fact being relied upon — the underlying mechanism
  (server-owned version counter + optimistic-concurrency conflict detection) is what's
  load-bearing and is grounded in RFC 7232's well-established conditional-request model.
- This scales fine to more than 2 devices later: the server is still the single
  arbiter regardless of how many devices sync through it, so nothing about this design
  needs to change when a third device is added.

## 2. Sync protocol shape

**Finding — data scale makes full-payload sync cheap.** Nine collections, a few
hundred records total, each record a small flat JSON object (the existing schemas in
`app.js` have on the order of 5–10 short string/date fields per record). A full JSON
dump of the entire dataset is very likely well under a few hundred KB — trivial to
transfer on a LAN even on a slow connection. This is a direct inference from the
existing data (`app.js`, all nine `loadCollection()`/`saveCollection()` call sites), not
an external source claim.

**Evaluation:**
- **(a) Full-dataset GET + per-record version, client diffs/merges locally:** simple,
  stateless, no server-side change log to maintain, no tombstone-compaction logic beyond
  what's described below, easy to reason about and easy to debug (you can literally
  `curl` the endpoint and read the whole state). Cost: sends more bytes than strictly
  necessary — irrelevant at this data scale.
- **(b) Delta/changelog-based sync (append-only operation log, client requests "give me
  everything since sequence N"):** the standard approach once data volume or client
  count gets large enough that full-state transfer is wasteful, but it requires the
  server to maintain an ordered, durable operation log, handle log compaction/retention,
  and requires clients to track a server-side cursor rather than just per-record
  versions. This is meaningfully more moving parts for a benefit (bandwidth savings)
  that doesn't exist at this app's scale.

**Recommendation:** use (a), full-dataset sync with per-record versions, per the
project's explicit "keep scope tight" principle — (b) is the textbook example of
over-engineering toward a problem this app doesn't have. Concrete shape for the Analyst
to turn into an exact spec:

```
POST /api/sync
Headers: X-Sync-Token: <shared secret — see Q4>
Request body:
{
  "deviceId": "device-<uuid>",
  "collections": {
    "books":       [ { "id": "...", "baseVersion": 4, "deleted": false, "fields": {...} }, ... ],
    "recipes":     [ ... ],
    "medications": [ ... ],
    "diagnoses":   [ ... ],
    "todos":       [ ... ],
    "shoppingList":[ ... ],
    "notes":       [ ... ],
    "links":       [ ... ],
    "courses":     [ ... ]
  }
}

Response body:
{
  "syncedAt": "2026-09-15T18:04:00Z",
  "collections": {
    "books":       [ { "id": "...", "version": 5, "deleted": false, "fields": {...} }, ... ],
    ... (same nine keys, full authoritative server state for each)
  },
  "conflicts": [
    { "collection": "medications", "id": "...", "note": "a conflicting edit was saved as a duplicate" }
  ]
}
```

The client's job on receiving a response: overwrite its local `localStorage` copy of
each collection with the server's returned state, and clear its `baseVersion` bookkeeping
to match the new `version`s. A record is only ever hard-deleted client-side after the
server confirms the deletion round-tripped (see the tombstone note below); it's a small
addition but it directly answers a gap the "diff by presence" version of plan (a) would
otherwise have.

**One concrete design point the Analyst needs, surfaced here because it's easy to miss:**
plain full-state diffing cannot distinguish "this record doesn't exist yet" from "this
record was deleted." If a record is simply removed from the array on delete, a device
that deleted something offline has no way to tell the server (or the other device)
about that deletion — the record will look, from the sync payload's perspective, like it
was simply never created. **This requires soft-delete tombstones**: add a `deleted`
boolean (and ideally a `deletedAt` timestamp) to the record instead of removing it from
the array on delete; the sync endpoint carries tombstoned records like any other
versioned record; the UI simply filters `deleted: true` records out of what it renders.
A retention window (e.g., permanently purge tombstones older than N days once all known
devices have synced past them) can be added later if storage becomes a concern, but at
this data scale it's not worth building up front.

## 3. What "resync automatically when the computer comes back online" requires

**Finding — `navigator.onLine`/the `online` event answer the wrong question here.**
MDN states plainly: "This property is inherently unreliable... you should not disable
features based on the online status, only provide hints" and that it "shouldn't be used
to determine the availability of a particular website" because "network problems or
firewalls might still prevent the website from being reached," and that browsers
generally "consider connection to LAN as online, even though the LAN may not have
internet access." **Confirmed** —
[MDN, Window: online event](https://developer.mozilla.org/en-US/docs/Web/API/Window/online_event) /
[MDN, Navigator.onLine](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/onLine).
More importantly for this exact scenario: the `online` event fires when *the browser's
own network interface* regains connectivity — but in the scenario described, the
**phone's WiFi connection never changes** (it stays connected to the same home WiFi the
whole time); it's the *computer* that goes from off to on. So the `online` event won't
even fire in the primary case this feature is meant to handle. It's not just
"unreliable" here — it's the wrong signal entirely, and should be treated as a free,
minor supplementary hook at best, never the core mechanism.

**Finding — Background Sync API is unavailable on iOS, and needs HTTPS regardless.**
Background Sync lets a service worker register a sync task that the browser will run
later even if the page isn't open — the API that actually matches "resync even though
the tab wasn't running JS." But per caniuse's current compatibility data: **neither
desktop Safari nor Safari on iOS supports Background Sync in any version**, confirmed
current as of the check performed. **Confirmed** —
[caniuse.com/background-sync](https://caniuse.com/background-sync). MDN's own page for
the API independently confirms it has "Limited availability" and is explicitly flagged
"not Baseline because it does not work in some of the most widely-used browsers" —
**Confirmed** —
[MDN, Background Synchronization API](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API).
If the phone in question is an iPhone, this option is entirely off the table regardless
of any other trade-off. Separately, Background Sync requires a registered **service
worker**, and service workers themselves require a **secure context** — MDN states
explicitly that "browsers also treat `http://localhost` as a secure context... [but]
plain HTTP LAN addresses like `http://192.168.1.5:8000` are NOT exempt" — **Confirmed** —
[MDN, Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API).
That means even on a non-iOS device, using a service worker here at all would force the
HTTPS decision in Q4 regardless of how that trade-off is otherwise weighed.

**Finding — polling has real, well-documented throttling limits while backgrounded.**
Browsers heavily throttle or suspend `setInterval`/`setTimeout` callbacks in inactive/
backgrounded tabs to save battery: Chrome clamps background-tab timers to roughly once
per second per independent timer, and more aggressively (on the order of once per
minute) for fully backgrounded tabs, a behavior documented directly by the Chrome team.
**Confirmed** —
[Chrome for Developers — Heavy throttling of chained JS timers beginning in Chrome 88](https://developer.chrome.com/blog/timer-throttling-in-chrome-88).
Mobile browsers are described as throttling more aggressively still, and a fully closed
or backgrounded tab on a phone (screen off, app switched away) commonly stops running
JS altogether rather than merely throttling it — this last point is **Likely** rather
than a specific citation for this exact scenario, since exact OS-level suspension
behavior varies by platform/browser and wasn't independently traced to a single spec,
but it's consistent with the throttling documentation above and with the general,
widely-known mobile OS practice of suspending background web content to save battery.

**Recommendation — concrete and decisive.** Do **not** build a service worker or use
Background Sync for this. The reasons compound: it's unavailable on iOS outright, it
forces the HTTPS/self-signed-cert decision even where it would otherwise be avoidable,
and it adds real implementation complexity (service worker lifecycle, cache
invalidation, registration/update edge cases) for a personal app that does not need
sub-second sync latency. Instead:
1. **Sync on load and on tab-visible.** Attempt a sync immediately when the app loads,
   and again whenever the tab transitions from hidden to visible (`visibilitychange`).
   This covers the actual real-world moment that matters: the user opens the app on
   their phone and it catches up with whatever changed while the computer was off/back
   on, with no waiting.
2. **Poll on a long interval while the tab is open and visible** — something in the
   30–120 second range is plenty for a personal tracking app with no real-time
   collaboration requirement; there is no need to chase a shorter interval, since the
   documented background-tab throttling above will silently defeat a short interval the
   moment the tab isn't focused anyway, so tuning for "instant" is wasted effort.
3. **Also listen for the `online` event as a free, cheap supplementary trigger** — it
   costs nothing to attach and occasionally helps (e.g., phone reconnects to home WiFi
   after being carried outside), but per the finding above, don't rely on it as primary.
4. **Explicitly accept the honest limitation:** if the phone's tab/app is fully closed
   or backgrounded when the computer comes back online, no sync happens until the user
   next opens the tab — at which point step 1 catches it up immediately. This is a
   reasonable, clearly-stated trade-off for "a personal app opened in a normal browser
   tab," matching what was asked for rather than reaching for PWA/service-worker
   machinery to chase a marginal, iOS-incompatible improvement.

## 4. Security of a self-hosted LAN server that now accepts writes

**Finding — home WiFi's own encryption does not protect this app's traffic from other
devices already on the same network** (the exact threat model named: a guest, a
neighbor with the password, a compromised IoT device). WPA2-PSK derives a per-client
session key from the network password during a "4-way handshake"; any device that
already knows the WiFi password can capture that handshake (or force a target device to
redo it) and then decrypt that device's traffic — this is standard, well-documented
behavior, not a novel or unusually sophisticated attack. **Confirmed** — see Wireshark's
own official documentation on the requirements for decrypting 802.11 WPA/WPA2-PSK
traffic:
[Wireshark User's Guide — 11.10. IEEE 802.11 WLAN Decryption Keys](https://www.wireshark.org/docs/wsug_html_chunked/Ch80211Keys.html)
and [Wireshark Wiki — HowToDecrypt802.11](https://wiki.wireshark.org/HowToDecrypt802.11).
In short: "being on the same home WiFi" is not, by itself, a meaningful security
boundary against the specific threat model the user named — those are exactly the
devices that already have the WiFi password.

**Finding — plain HTTP is cleartext by definition; that matters more given the data.**
HTTP has no built-in confidentiality; encryption is what TLS/HTTPS specifically adds.
web.dev's official guidance states HTTPS "prevents intruders from passively listening to
communications" and gives a directly analogous example: unencrypted traffic revealing
health-related browsing to eavesdroppers even without full content decryption, and notes
network compromise can happen at "a user's machine, a Wi-Fi hotspot, or a compromised
ISP." **Confirmed** —
[web.dev — Why HTTPS Matters](https://web.dev/articles/why-https-matters). Given this
app's data (medications, diagnoses) is exactly the sensitivity class of example used in
that source, plain HTTP is not a purely theoretical concern here.

**Recommended authentication mechanism: a single shared-secret token, not accounts.**
Generate (or let the user set) one random token; store it once on both devices (e.g. in
`localStorage`, entered once during setup) and once on the server; every sync request
carries it in a custom header, e.g. `X-Sync-Token: <token>`. The server rejects any
request with a missing or wrong token (401/403) before touching the datastore. Compare
using Python's `hmac.compare_digest()` rather than `==`, which the Python docs
specifically recommend to avoid timing-attack-based guessing of the correct value — a
cheap, stdlib-only defense-in-depth measure with no real cost to adding it correctly.
**Confirmed** — [Python docs, `hmac` — Keyed-Hashing for Message Authentication](https://docs.python.org/3/library/hmac.html).
This is deliberately *not* OAuth/full accounts — no login flow, no per-user identity, no
token refresh/expiry — which matches the explicit ask ("NOT full OAuth/user-accounts
machinery, that's overkill here") and the actual risk profile (one person, two-to-a-few
devices they personally control). The closest standard analogy, if useful framing for
the Analyst, is HTTP's own `Authorization: Bearer <token>` scheme (RFC 6750) — same
shape, simpler home-grown implementation.

**HTTP vs. self-signed HTTPS — the real trade-off, both sides stated plainly:**
- **Self-signed HTTPS pros:** encrypts the token and the health data in transit,
  closing the WPA2-PSK handshake-capture gap described above; this is the only way to
  protect data-in-transit from another authorized device on the same network.
- **Self-signed HTTPS cons:** triggers a full-page, unambiguous browser security warning
  on both devices (not a subtle indicator) because the certificate isn't signed by a
  trusted CA — this is standard, well-known browser behavior. Generating the
  certificate itself is **not achievable with Python's standard library alone**:
  Python's `ssl` module can *use* an existing cert/key to serve HTTPS, but has no
  facility to *generate* one — that requires either the external `openssl` CLI tool or a
  pip-installed library (`cryptography` or `pyOpenSSL`). **Confirmed** — this was
  checked directly; there is no stdlib path to certificate generation. This is a genuine
  (if narrow and one-time, not a runtime/import-time) departure from "zero dependency,"
  worth naming plainly rather than glossing over.
- **On the "should I even care, it's just my home network" framing:** OWASP-style
  guidance ("never allow self-signed certificates") is written for public-facing
  production services defending against strangers on the internet — a different risk
  profile than a private single-user home-LAN tool. Applying it dogmatically here would
  be over-engineering. But the underlying mechanism it warns about (cleartext
  interception) is concretely real here too, per the WPA2-PSK finding above — so the
  *reason* for the guidance still applies even though the *audience* it was written for
  doesn't quite match.

**Recommendation:** given the user explicitly named medications/diagnoses as the
motivating data and named the exact WPA2-PSK-adjacent threat model (guest, neighbor,
compromised IoT device — i.e., devices that already have network access), self-signed
HTTPS is the more defensible default here despite the setup cost, **combined with** the
shared-secret token (defense in depth: HTTPS protects the wire, the token gates who can
use the API at all). Concretely: generate the self-signed cert once as a manual setup
step (a one-line `openssl req -x509 ...` command, or, if `openssl` isn't already on the
machine, a one-time `pip install cryptography` used only by a small setup script — not
imported by the always-running server — which keeps the *runtime* dependency count at
zero even though the *setup* step isn't purely stdlib); trust the cert once per device
(most OSes/browsers let you permanently trust a specific self-signed cert rather than
click through a warning every time, which avoids the "warning fatigue habit" risk named
in the question — that risk is about repeatedly clicking through *different, varying*
warnings across many sites, not trusting one specific cert once on two specific devices
you own). **This is flagged as a genuine judgment call, not a slam dunk** — a reasonable
alternative is plain HTTP + token only, accepting the residual cleartext risk, if the
Architect judges the setup cost isn't worth it for this specific household's actual
threat exposure (e.g., no untrusted guests ever get the WiFi password). Both are
defensible; the brief's default lean is toward HTTPS given the data sensitivity named.

## 5. Implementation constraint check: is zero-external-dependency realistic?

**Finding — Python's standard library `http.server` module can do everything needed for
the server side except certificate generation (Q4).** `BaseHTTPRequestHandler` supports
implementing a custom `do_POST()` handler that reads `self.rfile` and parses it with the
`json` module — this is not built in as a convenience method, but is a small, standard,
well-documented amount of code. `ThreadingHTTPServer` handles concurrent requests in
separate threads out of the box. **Confirmed** — directly from
[docs.python.org — http.server](https://docs.python.org/3/library/http.server.html).

**Finding — the standard library documentation explicitly warns `http.server` is "not
recommended for production... only implements basic security checks."** **Confirmed**,
same source. This needs an honest, non-hand-wavy read rather than either dismissing it
or treating it as disqualifying: the warning is about internet-facing production
workloads — things like resilience against malicious/adversarial traffic at scale, rate
limiting, and hardened parsing against deliberately malformed requests are not built in.
For a server that only ever accepts connections from a small number of specifically
trusted devices on a private home LAN, gated by the shared-secret token from Q4, this
gap is a reasonable, explicitly-accepted trade-off — but it would **not** be reasonable
to expose this server directly to the public internet (e.g., via port forwarding without
a reverse proxy) using nothing but this handler. That's a real boundary worth stating
for future reference, not just for this cycle.

**Finding — a JSON file is a reasonable datastore at this scale; SQLite would be adding
capability the app doesn't need.** Nine collections, a few hundred records total — this
is the same order of magnitude of data the app already stores in `localStorage` per
collection today, just consolidated server-side. A single JSON file (mirroring the
existing `secondMemory.<collection>.v1` key shape, one file or one key per collection)
is simpler to reason about, inspect, and back up than standing up SQLite, and avoids
introducing SQL, a schema migration story, or a new mental model the rest of the project
doesn't otherwise need. This is a direct inference from the existing app's own data
shape and scale (`app.js`), not an external claim needing a citation.

**Two concrete correctness details worth flagging to the Analyst/Builder now, since
they're easy to get wrong with a hand-rolled file-backed store:**
- **Concurrency:** `ThreadingHTTPServer` serves requests on separate threads, so two
  near-simultaneous sync requests could race on a read-modify-write of the same JSON
  file. A single `threading.Lock` (Python stdlib) held around each read-modify-write
  cycle is sufficient at this request volume and is a standard, uncontroversial pattern
  for a single-process server.
- **Crash safety:** writing directly to the live data file risks a truncated/corrupt
  file if the process is interrupted mid-write. The standard mitigation is to write the
  new content to a temp file and then rename it into place. Python's `os.replace()` is
  documented as atomic on POSIX ("a POSIX requirement") and is *intended* to behave
  atomically on Windows as well, but a currently-open CPython documentation issue notes
  the Windows implementation (`MoveFileEx`) "is NOT guaranteed to be atomic" in all
  circumstances and "may silently fall back to a non-atomic... `CopyFile`" in some
  cases. **Likely** safe in the overwhelming majority of cases on Windows (the user's
  actual OS, per the environment context) but not a hard guarantee the way it is on
  POSIX — see the open issue at
  [python/cpython#143909 — "os.rename documentation about atomic replace misleading"](https://github.com/python/cpython/issues/143909).
  Combined with the in-process lock above (which already prevents the realistic failure
  mode — two threads in *this* process racing), the atomic-rename step is a reasonable
  extra layer of defense against a crash mid-write, not the primary correctness
  mechanism, so this residual Windows caveat is a minor, acceptable risk rather than a
  blocker.

**Recommendation:** stdlib-only (`http.server`, `json`, `threading`, `hmac`, `ssl` if
HTTPS is chosen) is realistic and not fighting the standard library — this is a genuine,
supported use case for `http.server`, just not the internet-facing-production use case
its own docs warn against, which doesn't apply here. The **only** place a non-stdlib
tool becomes necessary is one-time self-signed certificate *generation* (Q4), if that
path is chosen — and even there, the recommended approach (external `openssl` CLI, or a
pip package used only by a setup script never imported by the running server) keeps the
app's actual runtime dependency count at zero, consistent with the project's standing
constraint.

| 5 | Zero-dependency feasibility | Realistic with Python stdlib only (`http.server`/`ThreadingHTTPServer`, `json`, `threading.Lock`, `hmac`) for everything except one-time self-signed cert generation, which needs `openssl` CLI or a one-time pip-installed setup script (not a running-app dependency). JSON file is the right datastore at this scale; SQLite would be unnecessary. |
